# User
Codex /goal 实战之后发现，现在真正的门槛是验收标准

结论先说：Codex /goal 不是“一句话外包开发”。 它更像一个持续执行器。你给它一个目标，它会围绕这个目标继续推进、检查、修正，直到它认为完成，或者被暂停、清除、卡住、耗尽预算。

这类功能看起来很强。

过去你要不断告诉 Codex 下一步做什么。现在你可以直接设一个目标，让它自己往前跑。

但问题也在这里。

如果目标写得含糊，Codex 不会原地等你。它会带着这个含糊目标持续执行。普通 prompt 写错，最多浪费一轮；/goal 写错，可能会让它持续朝错误方向努力。

1. /goal 到底改变了什么
Codex CLI 0.128.0 新增的是 persisted /goal workflows。

关键不是多了一个 slash command，而是目标被持久化了。

简单说，以前你是在对话里不断发任务。现在你可以给 Codex 设置一个“当前目标”，Codex 会围绕这个目标继续工作。官方 release note 里提到的能力包括 app-server APIs、model tools、runtime continuation，以及 TUI 里的 create / pause / resume / clear。

能力
真实含义
/goal <objective>
设置一个持续目标，不是只执行一轮 prompt。
/goal pause
暂停当前目标，适合你发现方向不对时先刹车。
/goal resume
恢复之前暂停的目标。
/goal clear
清掉目标，避免 Codex 继续沿旧目标工作。
这就是它强的地方

它让 Codex 从“你一句我一句”的助手，变成“围绕一个目标持续推进”的执行器。

这也是它危险的地方

一旦目标不清楚，它不是停下来等你补需求，而是可能自己补脑、自己决策、自己继续做。

2. 真正的门槛不是会不会输入 /goal
很多人看到这个命令，第一反应是：

/goal 帮我把这个功能做完

/goal 帮我重构这个项目

这不是好的用法。

因为这两句话缺了最关键的东西：什么叫“做完”？什么叫“重构好”？

对人来说，含糊需求可以通过沟通慢慢补。但对持续执行的 agent 来说，含糊需求会变成执行风险。

验收标准才是 /goal 的真正门槛。

你要先告诉 Codex：哪些文件可以动，哪些不能动；做到什么程度算完成；必须跑什么检查；遇到什么情况必须停下来问你。

3. 一个可用的 /goal，至少要包含 7 件事
不要把 /goal 当 prompt 写。要把它当任务合同写。

模块
要写清楚什么
Objective
这次到底要完成什么，一句话说清。
Scope
允许修改哪些页面、模块、文件、接口。
Non-goals
这次明确不做什么，防止任务膨胀。
Acceptance criteria
满足哪些条件才算完成。
Validation
必须运行哪些测试、lint、type check、build。
Stop conditions
遇到哪些情况必须停下来问人。
Final report
完成后要汇报改了什么、怎么验证、还有什么风险。
这 7 项不是形式主义。

它们分别解决 7 个常见问题：目标跑偏、修改范围失控、任务越做越大、完成标准模糊、没验证、遇到风险继续硬干、最后不知道它到底做了什么。

4. 推荐做法：先用 ChatGPT, 最好是 GPT Pro 写任务合同，再交给 Codex
我不建议直接在 Codex 里写长目标。

更稳的做法是：先让一个强模型帮你把需求整理成任务合同，再把整理后的 objective 丢给 Codex。

你可以先问 ChatGPT Pro：

请帮我把下面这个开发任务整理成 Codex /goal 可执行的任务合同。

背景：

[项目背景、技术栈、当前模块]

目标：

[我要完成的功能或修复的问题]

请输出：

1. Objective：一句话目标

2. Scope：允许修改的文件、模块、页面、接口

3. Non-goals：这次明确不做什么

4. Acceptance criteria：逐条列出完成标准

5. Validation：必须运行哪些测试、lint、type check、build

6. Stop conditions：遇到哪些情况必须停下来问我

7. Final report：完成后需要汇报哪些证据

要求：

- 不要直接写代码

- 先指出任务边界是否含糊

- 如果缺关键条件，先问我

- 最后给出一段可以直接复制给 Codex /goal 的 objective

然后再把整理好的版本交给 Codex：

/goal Objective: [一句话目标]

Scope: [允许修改范围]

Non-goals: [明确不做的事]

Acceptance criteria: [完成标准]

Validation: [必须运行的验证命令]

Stop conditions: [必须停下来问人的情况]

Final report: [完成后汇报格式]

这一步看起来多了一层，但实际是省时间。因为你把 Codex 最容易误解的地方，提前变成了明确约束。

5. 如果是 UI 任务，别只给文字
UI 任务最容易翻车。

因为“高级感”“现代一点”“像 SaaS 一点”“好看一点”都不是验收标准。

如果你要让 Codex 做页面，最好先给它视觉边界：

可以给截图：现有页面、竞品页面、Figma 截图。

可以给参考图：用图像模型先生成一个大方向。

可以给组件约束：必须使用项目里已有的 shadcn/ui 组件。

可以给验收标准：移动端不破版、空状态有文案、loading/error 状态完整。

对独立开发者来说，这点很重要。

很多项目本来就用了 OpenSaaS、Next.js SaaS template、shadcn/ui 这类基础框架。你不一定要先画完整高保真原型，但至少要给 Codex 一个“视觉方向 + 页面状态 + 组件边界”。否则它很容易做成一个看起来能跑、但产品感很差的页面。

6. 现在使用 /goal，要注意这几个坑
这个功能还很新，不要按成熟功能来用。

坑一：文档还不完整

官方 changelog 和 release note 已经写了 /goal，但 slash command 文档的覆盖还不完整。早期用户需要自己看 changelog、issue 和 release note。

坑二：Plan mode 可能让目标看起来卡住

社区 issue 里已经有人反馈，在 Plan mode 下设置 active goal 时，界面显示目标 active，但 autonomous continuation 没有启动。遇到这种情况，不要以为 Codex 在后台跑，先检查当前模式。

坑三：长任务压缩后可能丢掉关键上下文

长任务里一旦发生上下文压缩，新的执行上下文可能更容易记住局部动作，而不是完整目标和验收要求。所以目标里要反复写清“完成前必须检查哪些条件”。

坑四：粘贴长 goal 可能出解析问题

有用户反馈，模板渲染后的 /goal 粘贴进去没有被当命令解析，而是变成普通文本。保险做法是：命令本身手动输入，长 objective 再粘贴进去。

8. 一个适合独立开发者的例子
假设你正在用 OpenSaaS 做一个产品，想加一个“免费试用 credits”功能。

不要这样写：

/goal 帮我把 trial credits 做好

要这样写：

/goal Objective: 为当前 OpenSaaS 项目新增 workspace-level trial credits 逻辑。

Scope: 只允许修改 billing、credits、workspace onboarding 相关模块；不要改 pricing 页面视觉设计。

Rules: trial_credits_enabled=true；grant_timing=email_verified；requires_payment_method=true；expires_after_days=3。

Acceptance criteria: 新用户验证邮箱并满足 payment method 条件后，workspace 获得 trial credits；credits 属于 workspace；member 消耗 workspace credits；owner 可查看 credits 状态。

Non-goals: 不接入真实支付网关；不修改套餐价格；不重写 onboarding UI。

Validation: 运行 type check、unit tests；如果没有测试，补充最小测试覆盖 credits grant 和 credits consume。

Stop conditions: 如果当前 schema 无法判断 workspace 与 subscription 的关系，先停下来汇报，不要自行重构账单模型。

Final report: 汇报修改文件、数据流、验证命令、未解决风险。

这才是 /goal 应该吃进去的任务。不是一句愿望，而是一份可执行、可检查、可停止的任务合同。

## 最佳部署方式：三层提示词

### 第一层：长期项目宪法，放进 `AGENTS.md` 或 `.harness/codex-rules.md`

这一层不要每次贴给 `/goal`，而是作为 repo 里的长期规则。它负责告诉 Codex：这个项目怎么验收、怎么停、哪些事情永远不能乱做。

官方 Codex 资料里也强调 Codex 会读 repo 里的指导文件并按其中要求运行测试；Codex CLI 本身支持不同 approval modes，长任务更适合在可控模式下推进，而不是一上来全自动放飞。([OpenAI][1]) ([OpenAI Help Center][2])

建议内容：

```md
# Codex Working Rules for FluffyFoundation

## Active plan

The active completion plan is `docs/harness/PLAN-zh.md`.
Historical plans under `docs/PlanDocs/0109_RootManagerControlPlane/` are context only.

## Execution model

Work on exactly one FF-* item at a time.
Do not start the next FF item until the current one has:
- implementation evidence,
- validation evidence,
- harness status update,
- handoff,
- unresolved risks recorded.

## Completion means

A task is not complete because status files say it is complete.
A task is complete only when implementation, tests, evidence, and review notes prove the acceptance criteria.

## Validation floor

Before marking any FF item complete, run the task-specific checks plus:

- pnpm verify
- pnpm build:all
- pnpm lint
- git diff --check

If `pnpm verify` fails, do not mark the FF item complete unless there is an explicit dated risk acceptance that explains:
- exact failure,
- why it is pre-existing or intentionally deferred,
- how it will be fixed,
- which later FF item owns the fix.

## Forbidden shortcuts

Do not:
- weaken tests to pass,
- broaden hotspot allowlists without explicit evidence,
- mark browser/runtime proof complete using only deterministic unit tests,
- treat status-transition commits as implementation,
- start FF-19 before FF-18 is reviewed,
- implement UI-only semantic mutation paths,
- bypass semantic command bus for AI/Canvas/CLI/API mutations,
- add direct Canvas/Rete/Svelte mutation paths for AI.

## Evidence requirements

Every FF item must produce or update:
- `.harness/status/current-phase.md`
- `.harness/status/current-task.md`
- `.harness/handoffs/<date>-FF-xx-*.md`
- `.harness/evidence/FF-xx/*` where possible

Final report must include:
- files changed,
- commands run,
- pass/fail results,
- evidence paths,
- known risks,
- whether the FF item is truly complete or only partially complete.
```

这一层的作用是：**防止 Codex 每次 goal 里忘掉项目纪律**。

---

### 第二层：每个 FF 的任务合同，不直接写进总 prompt

给每个剩余 FF 建一个任务合同文件，比如：

```text
.harness/goals/FF-18-review-contract.md
.harness/goals/FF-19-contract.md
.harness/goals/FF-20-contract.md
...
```

每个文件都按文章里的 7 项写：

1. Objective
2. Scope
3. Non-goals
4. Acceptance criteria
5. Validation
6. Stop conditions
7. Final report

这样做的好处是：你不用每次复制超长 goal，而且 Codex 可以先读合同，再执行。

### 第三层：真正输入 `/goal` 的内容要短，只指向当前合同

不要这样：

```text
/goal 把 FF-18 到 FF-24 都做完
```

而是这样：

```text
/goal Execute exactly one bounded task: FF-18 review and acceptance reconciliation.

- AGENTS.md
- docs/harness/PLAN-zh.md

- .harness/status/current-task.md
- .harness/evidence/FF-18/summary.md
- .harness/goals/FF-18-review-contract.md

Do not start FF-19.

Your job is to determine whether FF-18 is truly complete, incomplete, or complete-with-dated-risk-acceptance. If incomplete, implement only the missing FF-18 acceptance requirements allowed by the contract. If the missing requirements require browser/runtime/product integration beyond the contract, stop and report the blocker instead of faking completion.

At the end, update handoff/status/evidence and provide the final report requested by the contract.
```

这才是适合 `/goal` 的部署方式：**短 goal + repo 内合同 + repo 内长期规则**。

## 针对你当前 repo，第一步不应该直接做 FF-19

现在 `master` 的状态文件写的是 **FF-18 active**，FF-17 已接受。

如果按文章里的标准来评估，FluffyFoundation 现在已经比普通项目清晰很多；它有 `PLAN`、`QUALITY-GATES`、`BOUNDARIES`、status、handoff、evidence、`pnpm verify`。但如果你准备用 Codex `/goal` 继续做 FF-18～FF-24，**当前边界还不足以放心让它持续自动推进**。

我会给现在的验收体系打：

> **7/10：项目级规则清楚，单任务验收合同不够硬。**

## 已经做得好的地方

`docs/harness/QUALITY-GATES.md` 已经非常接近文章说的任务合同。它要求每个 task 声明 `PLAN ID`、允许修改边界、Non-goals、验证命令、evidence artifacts、rollback/recovery path，以及是否影响 Canvas/CLI/API parity 和 AI policy/audit。

`docs/harness/BOUNDARIES.md` 也把架构边界写得很清楚：UI 只渲染和捕获 intent，command/API 负责验证和语义 mutation，runtime 执行，transport 传消息，policy 决定权限，registry 描述能力。它还明确禁止 Canvas/Rete 直接改语义状态、AI 直接读 UI layout、控制命令缺 `scopeGroupId`、Display/Client/NodeExecutor 静默失败等。

AI 相关边界也不差。`AI-OPERATOR.md` 明确写了 AI 看到什么、不看什么、Command API 必须和 Canvas/CLI/API 共享、每个命令需要 schema、dry-run、policy、audit、history、rollback、structured result 和 observation hook。

所以从“有没有验收边界”来说，答案是：**有，而且比大多数项目强。**

## 不够好的地方

问题在于：这些边界还偏“项目宪法”，不是每个 `/goal` 可直接执行的“任务合同”。

按照文章里的 7 项来对照：

| 模块 | 当前情况 | 评价 |
|---|---|---|
| Objective | `PLAN-zh.md` 每个 FF 都有目标 | 基本清楚 |
| Scope | `BOUNDARIES.md` 和 status 文件有 allowed lanes | 有，但不够细 |
| Non-goals | 部分 task 有，例如 FF-18 status 写了 non-goals | 不够统一 |
| Acceptance criteria | PLAN / QUALITY-GATES / AI-OPERATOR 有 | 方向清楚，但不够可判定 |
| Validation | `pnpm verify`、build、lint、tests、harness 都有 | 很强 |
| Stop conditions | 基本是隐含的 | 明显不足 |
| Final report | handoff/evidence 有要求 | 有，但格式不够硬 |

最大问题是三个。

第一，**“完成”与“可接受延期”之间的边界不够硬。**
比如 FF-17 evidence 明确记录 `pnpm verify` 因 hotspot ratchet 失败，但 FF-17 仍被 status 接受并推进到 FF-18。 这不一定错，但对 `/goal` 来说很危险：Codex 可能学会“有失败也能继续推进”。

第二，**deterministic fixture 和 browser/runtime proof 的边界不够硬。**
FF-18 已经有大量 deterministic fixtures，但 evidence 多次写 browser/runtime proof deferred。 如果验收标准不把“fixture proof”和“真实 runtime proof”分开，Codex 很容易把 contract test 当成真实完成。

第三，**Stop conditions 不够显式。**
文章说得对，持续目标最怕“遇到不确定性继续硬干”。现在 `QUALITY-GATES` 有 review gate，但没有足够明确地告诉 Codex：什么时候必须停、什么时候不能自行扩大 scope、什么时候不能把 deferred 当 done。

## 对 `/goal` 来说，当前边界是否足够？

**不够。**

如果你只是让 Codex 做一个小 bugfix，现在的 harness 足够。
但如果你要让它继续完成 FF-18～FF-24，现在的边界还需要再加一层 **per-FF goal contract**。

原因是 FF-18 之后的任务都很容易被“假完成”：

- FF-18：AI deterministic core 可以通过，但真实 operator runtime 未必完成。
- FF-19：policy/redaction/audit 可以写测试，但真实安全边界未必完整。
- FF-20：observability 可以有 event types，但 operator console 未必真的可诊断。
- FF-21：golden scenarios 可以变成 fixtures，但不一定是真端到端。
- FF-22：load budget 可以有脚本，但不一定代表 show-mode resilience。
- FF-23：release/security checklist 可以写完，但不一定有真实 release proof。
- FF-24：文档可以写完，但 dogfood/rehearsal evidence 未必存在。

所以当前最需要补的不是更多代码，而是：

> **每个 FF item 单独写一个 `/goal` contract，并强制区分 “实现证据 / 验证证据 / runtime 证据 / deferred risk acceptance”。**

## 我建议你补 4 个东西

### 1. 新增 `docs/harness/ACCEPTANCE.md`

专门定义“什么叫完成”。

核心规则应该是：

```md
An FF item is not complete when status files say it is complete.

An FF item is complete only when:
1. implementation exists,
2. required validation passed,
3. evidence artifacts exist,
4. review/handoff records exact proof,
5. browser/runtime proof exists when required,
6. any deferred proof has dated risk acceptance,
7. the next FF item is not started before acceptance.
```

### 2. 新增 `.harness/goals/FF-xx-contract.md`

每个剩余任务一个合同。不要让 Codex 直接读总计划后自由发挥。

至少要有：

```md
Objective
Scope
Non-goals
Acceptance criteria
Validation
Stop conditions
Final report
```

### 3. 给每个 FF 加 “Proof Matrix”

比如 FF-18：

```md
| Criterion | Deterministic test | Runtime/browser proof | Evidence path | Status |
|---|---|---|---|---|
| Semantic context excludes UI noise | yes | not required | ... | proven |
| AI command bus parity | yes | partial | ... | proven |
| Display breathing visible output | contract only | missing | ... | deferred |
| Gyro flashlight rhythm | contract only | missing | ... | deferred |
```

这个矩阵能防止 Codex 把“有测试”自动等同于“产品完成”。

### 4. 明确 risk acceptance 格式

比如：

```md
## Dated Risk Acceptance

Risk:
Owner:
Date:
Why accepted:
What proof is missing:
Why it is safe to continue:
Follow-up FF item:
Blocking severity:
```

否则“deferred”会变成万能通行证。

## 最终判断

**现在的验收边界清晰，但不够可执行；适合人类 reviewer 看，不足以直接喂给 `/goal` 做长期自动推进。**

你已经有了很好的项目级规则：

- `QUALITY-GATES.md` 定义 gate；
- `BOUNDARIES.md` 定义架构边界；
- `AI-OPERATOR.md` 定义 AI 验收方向；
- `package.json` 和 CI 已经把 `pnpm verify` 作为主验证入口；
- status/handoff/evidence 体系已经存在。

但你还缺一层：

> **Codex 可执行的、每个 FF 独立的验收合同。**

所以我的建议是：**先不要直接开 FF-19。先让 Codex 做一个 FF-18 acceptance reconciliation，把“哪些真的完成、哪些只是 fixture、哪些 deferred”整理成 proof matrix。然后再按 FF-19、FF-20……逐项开 `/goal`。**

## 现在最稳的用法

不要把完整任务合同直接塞进 `/goal`。改成：

### 1. 把长合同写进 repo 文件

例如：

```text
.harness/goals/FF-18-review-contract.md
```

### 2. `/goal` 只写短入口

在 Codex 里手动输入 `/goal`，然后粘贴短文本：

```text
Execute FF-18 review and acceptance reconciliation only.

Read:
- AGENTS.md
- docs/harness/PLAN-zh.md
- docs/harness/QUALITY-GATES.md
- docs/harness/BOUNDARIES.md
- .harness/goals/FF-18-review-contract.md
- .harness/evidence/FF-18/summary.md
- .harness/status/current-task.md

Do not start FF-19.

Determine whether FF-18 is complete, incomplete, or complete-with-dated-risk-acceptance. Use the contract file as the acceptance boundary. Update evidence/status/handoff only after validation.
```

这样 `/goal` 本体短，真正的验收标准在文件里，比较不容易触发 TUI bug。
